# Windows 完整收口与旧能力迁移设计

日期：2026-08-22

状态：待用户复核

工作目录：`C:\Users\example\Desktop\XS`

## 1. 目标

在把 XS 交接给另一台设备之前，完成所有能够且应该在当前 Windows 设备上实现、验证和留证的工作。交接后只允许留下确实依赖其他操作系统、其他硬件、外部账号或人工授权的项目，不把普通工程缺口包装成“换机后再做”。

交付结果必须同时满足：

1. Windows 能从不携带 `node_modules` 和构建产物的交接目录完成安装、构建、配置、启动、停止和再次启动。
2. DSH 仍是唯一 Agent Runtime、会话、模型、审批和工具流水线内核；旧 Python 小蛇只能作为受限能力 Provider 存在。
3. 中文路径、中文指令和中文 JSON-RPC 数据在 Windows 上全程保持 UTF-8。
4. Windows UIA、截图、坐标映射、点击、输入、按键、动作后验证、陈旧视口拒绝和可用 DPI 场景获得真机证据。
5. 旧项目中适合新架构、能够在 Windows 验收的能力完成迁移；不适合迁移的能力有逐项理由和去向。
6. 三个现有 Git 工作树的用户改动和平台差异均被保留，不通过 reset、clean 或覆盖来制造“干净”结果。

## 2. 当前基线与已知缺口

XS 是三个相互独立的 Git 工作树：产品 Bundle 根仓库、`runtime/DSH`、`runtime/xiaoshe-legacy`。它们当前都有既存未提交状态。实施只在明确归属的仓库中修改文件，并在每一阶段前后记录 HEAD 与工作树状态。

当前 Windows 隔离验证已经暴露以下确定性缺口：

- 根项目的类型检查和构建可通过，但测试包含 macOS/Linux 解释器与 shell 的硬编码。
- Windows 上可用解释器是 `python`/`py -3`，默认 `python3` 可能落到 Microsoft Store 别名并失败。
- Python `-I` 会忽略 `PYTHONUTF8` 等环境变量，当前桥接的中文 stdio 存在乱码风险。
- 子进程结束竞态在 Windows 可能抛出 `EINVAL`，不能只把 `ESRCH` 视为已退出。
- 私有截图目录目前主要依赖 POSIX mode；Windows ACL 的实际私有性尚未形成实现与证据闭环。
- 交接校验把 Windows 无法表达的符号链接、可执行位和变化中的工作树指纹当作失败，尚未形成跨平台语义。
- 现有 `node_modules` 是来自其他平台的运输残留，不能作为 Windows 可复现依赖基线。
- Windows UIA 与真实桌面动作、DPI、统一启动/停止入口仍缺真机验收。
- 旧能力虽保留在 `runtime/xiaoshe-legacy`，但尚未完成“已由 DSH 提供 / 应迁移 / 暂留 Provider / 淘汰”的能力账本。

## 3. 方案选择

### 方案 A：只修复启动与单元测试

优点是改动小、速度快；缺点是无法证明 UIA、DPI、ACL、真实动作和交接可复现性，不符合“把本机能做的都做完”。不采用。

### 方案 B：一次性把旧 Python 全部重写成 TypeScript

优点是表面上减少语言数量；缺点是同时改变运行时、实现语言和产品架构，回归面过大，也会重复 DSH 已有能力。无法在交接前可靠收口。不采用。

### 方案 C：Windows 基线收口后按能力契约渐进迁移

先让现有 DSH + XS + 受限 Python Provider 在 Windows 上可复现并完成真机闭环，再用统一验收集筛选和迁移旧能力。每项替换实现必须通过同一契约后才能移除旧依赖。采用此方案。

## 4. 架构边界

### 4.1 唯一内核

- DSH 拥有 Agent 循环、模型路由、会话、计划、审批、沙箱、工具注册与执行轨迹。
- XS Bundle 拥有小蛇产品层、桌面工具契约、Windows 启停与桥接生命周期。
- ModLens 继续负责图片语义理解，不在 XS 内复制第二套视觉模型。
- `runtime/xiaoshe-legacy` 只提供尚未原生替换的底层桌面能力，不得重新暴露旧模型循环、会话、审批或工具注册表。

### 4.2 Windows 原生适配层

Windows 差异集中在明确的适配边界中：

- 解释器发现与 UTF-8 启动参数；
- 子进程创建、终止与孤儿进程检查；
- 私有临时目录和 ACL；
- PowerShell 安装、启动、停止与健康检查；
- UIA、显示缩放和屏幕坐标证据；
- Windows 可表达的交接完整性语义。

核心工具协议、审批规则、视口版本和动作后验证不为 Windows 另建分叉。

## 5. Windows 收口工作流

### 5.1 可复现依赖与解释器

- 删除“运输 `node_modules` 即可运行”的隐含假设；安装器识别平台不匹配或损坏的依赖并以锁文件重建。
- 使用显式、可测试的解释器选择顺序，优先尊重 `XIAOSHE_PYTHON`，再选择当前 Windows 中真实可执行的 Python。
- Bridge 使用 Python 自身的 UTF-8 模式参数，不依赖会被 `-I` 忽略的环境变量。
- 测试覆盖中文路径、中文请求、中文响应、错误消息和非 ASCII 临时目录。

### 5.2 进程与启停

- Windows 启动器负责构建 Bundle、准备 DSH、配置 Profile、启动唯一 DSH Web 实例并等待健康端点。
- 停止器只结束由 XS 记录和拥有的进程树，不按端口盲杀其他程序。
- 桥接进程按需创建并随插件卸载或宿主退出达到静止。
- `ESRCH`、Windows 已退出竞态和受控的 `EINVAL` 按实际进程状态处理；其他终止错误继续显式失败。

### 5.3 文件私有性

- 截图与运行期证据写入当前用户专属临时目录。
- POSIX 使用 mode 验证；Windows 使用 ACL/继承状态验证，不能用 `0777` 与 `0700` 的表象差异误判安全性。
- 退出时清理运行期证据；需要保留的验收截图复制到明确的、脱敏的 evidence 目录。

### 5.4 交接完整性

- 清单继续覆盖三个仓库的内容与 Git 状态，但区分“内容损坏”和“平台无法表达的元数据”。
- Windows 对符号链接和 executable bit 使用可复现的 Git 内容语义，不要求 NTFS 工作树伪装成 macOS mode。
- 工作树快照应能表达用户已有修改，又不因验证过程中生成的依赖、构建物、日志和清单本身产生漂移。
- 接收器必须从清单、锁文件和源码重建，不依赖发送设备缓存。

### 5.5 Windows 真机验收

优先使用系统计算器、记事本和专用无敏感内容验收窗口，避免触碰用户真实业务数据。最小真机链路为：

1. 启动唯一 DSH + XS 实例并确认健康状态；
2. `screen_observe` 获得真实 Windows 截图和 UIA 元素；
3. 对安全目标完成经 DSH 一次性审批的点击；
4. 完成中文输入与按键；
5. 每次动作后重新观察并证明截图或 UIA 发生预期变化；
6. 重用旧视口时明确拒绝；
7. 在当前设备能够设置的缩放比例上复现坐标映射；对不能同时覆盖的比例记录硬件/会话限制，不伪造通过；
8. 停止后确认端口、DSH 宿主和 Python Bridge 均已退出。

## 6. 旧能力迁移

### 6.1 能力账本

以用户可观察能力而不是旧文件数量为单位建立账本。每项归入以下一种状态：

- `DSH 已提供`：直接使用 DSH，不迁移重复实现；
- `XS 已提供`：由当前 Bundle 维护并补齐 Windows 验收；
- `应迁移`：符合唯一内核，存在明确用户价值，且可写契约测试；
- `暂留 Provider`：有价值但原生替换风险高，继续通过受限 Python 接口提供；
- `淘汰`：重复、过时、不可维护、突破审批边界或与产品方向冲突；
- `外部阻塞`：必须依赖其他设备、系统、账号或人工授权。

### 6.2 迁移准入条件

旧能力只有同时满足以下条件才迁移：

1. 不创建第二套 Agent、会话、模型、审批或工具体系；
2. 能通过 DSH 工具或正式扩展点接入；
3. 权限与危险动作默认失败关闭；
4. 输入、输出、错误和生命周期可以形成稳定契约；
5. 能在当前 Windows 设备上自动化或真机验证；
6. 迁移收益高于长期兼容成本。

### 6.3 优先顺序

先处理与 Windows 交付直接相关的能力：统一 CLI/TUI 入口、Provider 就绪状态、任务/计划/后台工作的投影、桌面证据持久化边界、多显示器能力评估。其后再审计旧工具、记忆、工作流和其他 Provider。

旧实现不会在替代实现尚未通过同一验收集时删除。若只完成能力盘点而未完成迁移，状态必须写为“已审计，未迁移”，不能写成完成。

## 7. 测试与证据策略

每个行为变更遵守测试先行：先写能够在 Windows 复现缺口的失败测试，再做最小实现，最后运行相关测试与全量门禁。

门禁分为四层：

1. 单元/契约：解释器发现、UTF-8、终止竞态、ACL 判定、清单平台语义、旧能力适配契约；
2. 工程：TypeScript 检查、Vitest、Python unittest、生产构建；
3. 组合：从干净依赖状态安装 DSH + XS、配置 Profile、HTTP 健康检查、卸载/停止静止性；
4. 真机：Windows 截图、UIA、点击、中文输入、按键、动作后验证、陈旧视口和 DPI。

证据必须记录日期、Windows/Node/Python 版本、三个 HEAD 与工作树摘要、精确命令、通过/失败计数和必要截图。模拟测试不能替代真机结论，单次公开页面冒烟不能替代发布批准。

## 8. 失败处理与回退

- 某项修复失败时只回退该项明确产生的文件，不回退用户原有改动。
- DSH 内核修改是最后手段；优先使用 XS 外部 Bundle 和稳定扩展点。若确实必须修改 DSH，单独提交并记录升级影响。
- 旧能力迁移按能力拆分，Provider 保持可回退，直到新实现通过同一验收集。
- 不清理三个工作树；构建物和依赖只按安装器的明确范围处理，并在操作前验证目标路径属于 XS。

## 9. 完成定义与交接边界

“Windows 完成”要求：实现、自动化测试、真实组合、失败路径、真机证据、文档和可重复命令全部齐备。仅写完代码不算完成。

最终交接报告把事项分成四类：

- `已完成并验证`；
- `已实现但受明确外部条件限制，未真机验证`；
- `已审计且不建议迁移`；
- `只能在另一台设备完成`。

允许留给另一台设备的典型事项仅包括 macOS 签名/公证、macOS TCC/AX 真机复验、另一台设备独有的硬件或显示器组合，以及必须由用户在外部账号完成的授权。Windows 安装、启动、UTF-8、ACL、UIA、可用 DPI、真实安全桌面动作、测试门禁、旧能力账本和可在本机完成的迁移不得留作泛化待办。

## 10. 实施顺序

1. 冻结三个仓库基线和验证环境；
2. 修复并测试 Windows 工程基线；
3. 完成 Windows 安装、启停、权限和交接语义；
4. 完成 DSH + XS 真实组合与 Windows 桌面真机验收；
5. 建立旧能力账本并按优先级迁移可收口项；
6. 重新运行完整门禁，生成 Windows 证据与最终交接边界。

## 0. "商业产品级"的定义（先对齐口径，再谈施工）

**本文按此口径解释你的目标**（若理解错了，这是方向级改动，推倒重排）：

> 商业产品级 ≠ 做多用户 SaaS（总规划非目标写死单人双机，本文不推翻）。
> 商业产品级 = **质量达到"可以承载星见、可以当商品交付"的工程水准**，五条硬杠：
> 1. **可复现的可靠性**——pass^3 度量，不是"这次跑成了"；
> 2. **不可信内容进不了动作路径**——安全从黑名单升级为数据流约束，不是"劝模型别听坏话"；
> 3. **每笔花费可见**——token/请求/缓存命中全程记账；
> 4. **每次改动有客观标尺**——eval 套件 + CI，不是人肉回归；
> 5. **每个里程碑过对抗式审查**——延续项目护城河工序。

**目标抬高后，从"可选"翻转为"必修"的清单**（六路抽取逐条核出）：
容器沙箱后端(1a) · 出站白名单默认 off(1b) · 污点标签含子 agent 继承(1c) · 注入回归套件入 CI(1e) · prompt caching 全套(2b) · 压缩可回捞分页(2c) · Docker eval 隔离(3c) · 真 Kimi pass^k 成绩单 · 流式 idle 看门狗(#5) · use_root contextvar(#33) · MCP 有界读 · jobs 硬背压 · 收尾独立验证默认开(5c) · 并发三护栏(5e) · episodic 落盘脱敏(5b)。

**继续不做的**（YAGNI 仍然生效）：多用户/云端形态与 Linux 服务器常驻（"重启并登录后照跑"边界写明契约即可）、自训 grounding 模型、全桌面像素控制、SIXEL 终端真图、形式化验证。**显式缓行**：并行写隔离（worktree，差距 #3）——绑定 P5-5e 真实使用暴露踩踏需求后再立项。

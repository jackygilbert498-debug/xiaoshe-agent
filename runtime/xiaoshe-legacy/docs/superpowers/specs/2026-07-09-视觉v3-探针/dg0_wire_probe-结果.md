# DG-0 承重探针结果（2026-07-09 真机跑）

端点 `https://api.kimi.com/coding/v1`，模型 `kimi-for-coding`。三查全绿：

| # | 序列 | payload 带 tools[] | 结果 | prompt_tokens |
|---|---|---|---|---|
| 1 | baseline：单条 user 带图（红） | 否 | ✅ 答「红」 | 351 |
| 2 | **★承重**：system+user+assistant(tool_calls)+tool(text)+**user([text,图])**（绿） | **是** | ✅ 答「绿」 | 478 |
| 3 | 优化：图放进 **tool 角色** content 数组（蓝） | 是 | ✅ 答「蓝」 | 438 |
| 4 | **★承重·流式**：同 #2 但走 `chat(on_delta=…)` 流式路径（绿） | 是 | ✅ 流式也答「绿」 | — |

## 结论（对 P3 设计的影响）

- **承重假设成立**：Kimi coding 端点接受「tool 结果之后、以 user 消息中途插图」，且模型**真读到**了这张中途插入的图（醒目纯色 + 冷门问题，答对色=读到而非猜），payload 同时带 tools[] 也不 400。→ 综合方案 §2.2 的**优雅路径可用**，无需退兜底。
- **额外收获（查 3）**：图直接放进 **tool 角色**消息的 content 数组同样 200 且被读到 → materialize 时可把"指针 tool 消息"在发送副本里替换成"带图 tool 消息"，省掉合成尾部 user 消息（更自然的顺序）。两条路都可用，v0 先用更简单、缓存更友好的**尾部 user 合成**（综合方案主路径），tool-role 作为已验证的备选。
- **仅验了非流式 `_post`**。流式 `_post_stream` 走同一消息形状、风险已大幅降低，留 v0 收尾补一发流式 smoke。

不变式未受影响：history 里仍**只存指针文字、base64 只在发送副本临时出现**——探针验的是"发送形状"，不改"落盘形状"。

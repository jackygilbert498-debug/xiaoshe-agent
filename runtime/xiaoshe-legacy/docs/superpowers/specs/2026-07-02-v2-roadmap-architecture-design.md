# Harness v2 · 总体规划与目标架构 · 设计文档

> 2026-07-02 定稿。由用户（架构师/PM/QA）与 Claude 共同澄清、逐节确认后落档。
> 本文是 v2 的「设计」；每个里程碑动工前另出更细的实施计划（拆到一次能验收一块的粒度）。

---

## 1. 目标与非目标

**目标终态：先通用后接管。**
v2 = 用户日常真用的通用个人 agent（写代码/改项目、资料研究/联网检索、文件整理/本地自动化、视频创作工作流四类活都干），在真实使用中磨出稳定性；「是否接管星见」留到路线尾部的决策关卡 G，用真实使用记录做依据，届时由用户拍板。

**非目标（明确不做）：**
- 不做多模型路由/降级（模型锁定 Kimi `kimi-for-coding`，`model_fn` 注入接缝天然保留，将来要换有口子）。
- 不做多用户/云端服务形态（单人双机场景）。
- 不为「机制覆盖度」而造用不上的东西（YAGNI）。

## 2. 现状盘点（2026-07-02 实测）

- v1 六阶段完成 + 整体夯实：8 内置工具、权限三态闸门、记忆、压缩、子 agent、会话存档、后台任务（进程内）、MCP（stdio）。
- 本机（macOS）实测：82 条测试 **75 绿 / 7 红**。7 条红同根因——测试把工作区 patch 到系统临时目录，macOS 的 `/var` 是指向 `/private/var` 的符号链接，权限闸门核对路径时展开了链接、测试给的地址没展开，两边对不上被误判「越出工作区」。**是测试代码的跨平台问题，不是 harness 运行时缺陷**（真工作区地址在启动时已展开）。
- 实链验证：本机真连 Kimi 成功（代理 127.0.0.1:7897 在跑、key 有效、Mac 自带 curl 可用）。
- 文档残留 Windows 语境（`D:\Harness` 提示语、`curl.exe/schannel`、`set PYTHONUTF8` 等）。
- 已知弱点（细读代码发现，v2 内修）：`remember` 免审批可写长期记忆、无上限无删除口；MCP 工具一次 JSON-RPC error 即误杀整个 server 连接；命令文本扫描可拼串绕过（契约已自认「防手滑不防对手」，维持定位不变）。
- 生产级差距清单见 `docs/离生产级还差什么.md`（12 条）。

## 3. 需求与约束

- **双机并用**（macOS + Windows）：跨平台从「差距」升级为**硬需求**，每个里程碑双平台测试都要绿。
- **同步方式**：私有 git 仓库（代码 + 记忆）；`.env` 密钥永不进仓，走私密渠道。
- **推进节奏**：逐功能验收——里程碑内部拆小块，每块交付即验收；任何时刻仓库都是「完整能开的车」。
- **技术底座不变**：纯 Python 标准库零依赖；Kimi + curl 传输；既有安全拍板全部继承（无 TTY 默认拒、危险一律 ask 可答 a、敏感文件连读都拒）。
- **交付纪律**：每功能 = 代码 + 中文名测试 + CONTRACT.md 更新 + 用户亲自验收步骤。

## 4. 目标架构（顶尖 CLI 同构）

对齐 Claude Code / Kimi CLI 的形态：**无常驻服务；状态落盘为王；借系统调度器；多开进程即并行。**

```
你敲字                 脚本/系统调度器
   │                        │ 到点唤起
   ▼                        ▼
┌──────────┐        ┌──────────────┐      ┌─────────────────┐
│ 交互对话  │        │ 无头模式(新)  │      │  系统调度器      │
│ run.py   │        │ 一进一出免值守 │◀─────│ launchd/任务计划 │
└────┬─────┘        └──────┬───────┘      └─────────────────┘
     │                     │
     ▼                     ▼
┌────────────────────────────────┐       ┌──────────────────┐
│  Agent 引擎（v1 心脏不变）       │ ◀───▶ │  状态目录         │
│  循环·8 工具·权限闸门·压缩·子agent│       │ 记忆·会话·任务·日志│
└────┬──────┬──────┬──────┬─────┘       └──────────────────┘
     ▼      ▼      ▼      ▼
  Kimi API  MCP   本地文件  Web 工具(新)
  (curl)  (星见桥等) 与命令   抓取·搜索
```

- **两个入口，一台引擎**：交互对话照旧；新增无头模式（单命令进出，供脚本与调度器调用）。多会话并行 = 多开进程。
- **调度借系统的**：任务登记落盘，harness 提供命令把任务装进 launchd（Mac）/ 任务计划（Windows）；到点由系统唤起无头模式。重启不丢——记事的是系统，不是某个必须活着的进程。
- **状态落盘为王**：记忆、会话档案、后台任务档案、日志统一收进状态目录；任何进程死掉状态都在。
- **v1 心脏原样保留**：循环/工具/权限/压缩不动，82 条测试基线继续有效。

**架构复议记录**：曾考虑「常驻服务 harnessd + 薄前端」方案，对比顶尖 CLI 后放弃——顶尖 CLI 均无守护进程，daemon 的双平台运维成本（自启、拉活、升级停服）对单人场景不划算。「MCP 是否需要常驻连接」留到关卡 G 前再评估。

## 5. 关键设计决策（七条，均已确认）

1. **无人值守安全——创建时刻 = 审批时刻。** 无终端默认拒（继承）；定时任务在交互模式创建时一次性批好该任务的工具白名单（含路径限定，如仅 Downloads），无头运行照单放行、单外一律拒并记日志；敏感文件（`.env`/私钥等）**任何模式连读都拒，无豁免**。
2. **双机同步细则。** `memory.json` 进 git 共享（需从 `.gitignore` 摘出并确认不含敏感内容）；会话档案、日志、任务登记留本机不同步；`.env` 走私密渠道。记忆冲突按「两边都留、自动去重」合并，配一个小命令。
3. **Web 工具选型。** `web_fetch`：curl 下载 + 标准库解析正文，大页面落盘、给模型摘要+路径（防灌爆上下文）。`web_search`：优先实测 Kimi API 自带联网搜索能否用于本线路（M5 第一个验收点），不行退到抓搜索结果页。**网页内容 = 不可信数据**：加「勿当指令执行」前缀 + 截断，与 MCP 输出同一待遇。
4. **多开进程防冲突。** 会话档案一会话一文件，「接着上次」升级为可选会话列表；`memory.json` 等共享文件加跨平台文件锁（标准库 `fcntl`/`msvcrt`）；日志按会话分文件。
5. **后台任务跨重启。** 任务档案（命令、pid、日志路径、状态）落盘；进程活着可查可停，重启后历史任务的输出与退出码仍可查；启动时核对 pid 存活，清理孤儿档案。
6. **补两个已知弱点。** `remember` 加条数与长度上限 + 「查看/删除记忆」命令（记忆对用户透明）；修「MCP 一次参数错误误杀整个 server 连接」——普通 JSON-RPC error 收敛为该次调用的 is_error，只有超时/EOF 才断开摘除。
7. **不变项写进契约。** 零依赖；锁 Kimi + curl；三件套 + 亲自验收步骤，逐里程碑不缺席。

## 6. 分阶段路线图

每个里程碑独立可停、可回退（git 里程碑基线）；内部逐功能验收。

| # | 里程碑 | 交付 | 用户验收（示例） |
|---|---|---|---|
| M0 | **换机闭环** | 修 7 条红（测试 patch ROOT 前先展开路径，权限层同步加固）；清文档 Windows 残留；建私有 git 远程、跑通双机同步；记忆合并小命令 | Mac 82 条全绿；双机 git 一来一回不丢东西 |
| M1 | **引擎整备** | 状态目录收拢；会话档案多文件化 + 会话列表恢复；共享文件锁 | 两个终端同时对话互不干扰；重启后从列表挑会话恢复 |
| M2 | **无头模式** | 单次执行入口；任务白名单机制 | 一句命令免值守干完活；越权任务被拒且留日志 |
| M3 | **定时调度** | 任务登记落盘；launchd/任务计划安装命令；执行历史可查 | 建「每小时记一行时间戳」任务，重启电脑照样跑 |
| M4 | **后台跨重启** | 任务档案落盘；重启后可查历史 | 睡前起长任务，次日开机能问到结果 |
| M5 | **Web 工具** | `web_fetch`；`web_search`（先实测 Kimi 联网，备胎抓结果页） | 「看看这个网址讲了啥」「搜 X 并汇总」 |
| M6 | **安全夯实** | 修 remember/MCP 弱点；对 M1–M5 新代码跑对抗复盘并修真问题 | 复盘报告 + 对应中文测试全绿 |
| M7 | **可观测性** | 每会话 token/费用统计；日志查看命令 | 问「这个月大概花了多少」能答 |
| M8 | **真实使用期（毕业考）** | 四类活各干若干真实任务；问题清单收敛 | 连续日常真用一段时间，不再冒新的大问题 |
| G | **接管星见评估（关卡）** | Windows 机接真实星见桥，实测驱动总台工具；届时评估 MCP 是否需要常驻连接 | 拿 M8 使用记录 + 接桥实测，**用户拍板**接不接管 |

**顺序逻辑**：M0 先行（红着的基线上不盖楼）；M1 是多进程地基；M2 是 M3 前提；M4、M5 相对独立可按需对调；M6 固定在新代码成批之后；M8 之前不谈接管。

## 7. 风险与对策

| 风险 | 对策 |
|---|---|
| Kimi 联网搜索在 coding 端点不可用 | M5 首个验收点即实测；备胎方案（抓搜索结果页）不阻塞功能 |
| launchd 与任务计划差异大 | 各写各的安装器；双平台测试各自跑；M0 的 git 同步是前提 |
| 逐功能验收节奏慢于 v1 | 每个里程碑均为完整可停点，不存在烂尾形态 |
| 双机 git 分叉 | 纪律「动手前先 pull」；记忆冲突自动合并工具（M0） |
| 无头模式扩大攻击面 | 创建时审批 + 白名单 + 敏感硬护栏无豁免 + 全程日志（M2 含对应中文测试） |
| chat/completions 非幂等重试重复计费（v1 遗留取舍） | 维持现状；M7 花费统计让问题可见，量大再治 |

## 8. 测试与验收策略

- **回归基线**：82 条为底，逐里程碑只增不减；`python -m unittest discover -s tests -v` 双平台全绿是每个里程碑的收尾条件。
- **离线为主**：新功能沿用 model_fn/approver 依赖注入 + mock，完全离线可测；调度/锁/落盘类用临时目录（**统一先 resolve 再 patch**，M0 固化为测试工具函数）。
- **实链与真人式验收**：每个里程碑收尾按既有纪律用真 Kimi + 自然对话实测一遍新能力（沙盒工作区）。
- **对抗复盘**：M6 集中一轮；发现的修复固化为回归测试。
- **中文测试名**：测试名说清行为，用户看名字 + 绿/红即可验收。

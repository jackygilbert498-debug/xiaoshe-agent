# 自我扩展能力方案 · agent 自己"装工具"/"造工具"

> 状态：**规划中，先不做，待甲方拍板**（2026-07-11 记）。这是全项目**想象力最大、也最危险**的一步，
> 设计没想透不动代码。本稿只把想法、现状、风险、分阶段路线、待决策点钉清楚，供后续 brainstorming 起步。

## 0. 一句话
让小蛇能：**① 从 GitHub/生态"下"现成工具（= 装 MCP server）**、**② 自己"造"工具（写代码变成新工具）**。
两条路都可行，咱们架构已经铺了一半；难的不是实现，是**在不炸掉现有安全模型的前提下做**，须**人始终在环 + 分阶段**。

## 1. 动机
甲方想法（2026-07-11）："我们给他装了很多工具，能不能让他自己也学会从 GitHub 上去下工具、或者自己去制作工具。"
= 从"我们喂给它固定一套工具" → "它能自己扩充能力"。这是 agent 从"工具使用者"向"工具获取者/作者"的跃迁。

## 2. 现状盘点（已有的一半 vs 缺的一半）

### 路 A：从 GitHub/生态下工具 = 装 MCP server
MCP 是 agent 生态的"工具包管理器/USB 插座"，GitHub 上现成 MCP server 成百上千。
- **已有**：`mcp_client.connect_configured()` + `mcp.json` + `mcp__` 前缀工具 + `all_specs()` 合并声明——**小蛇已经会用外部 MCP 工具**（甲方"装了很多工具"多半即此）。
- **缺**：让小蛇**自己发现 + 安装**（搜 MCP registry/GitHub → `git clone`/`npx`/`pip` 装 → 写进 `mcp.json` → 重连）。这些动作它靠现有 `run_command` **技术上已能做**，缺的是**流程 + 信任闸**。

### 路 B：自己造工具 = 写代码变成新工具（拆成 A2a / A2b 两条，风险与排期天差地别）
路 B 不是一件事，得按"产物要不要跑代码"劈成两条独立子线：

**A2a——markdown/技能类（`SKILL.md`，可早做）**
- 产物是**纯文本技能卡**（`SKILL.md`：什么时候用、怎么做、惯用法），**不含可执行代码 → 无需沙箱**。
- 落地路径最短：接**现有 `spawn_subagent` + Reflexion**——让子 agent 把一段成功经验总结成技能、写进技能库，下次按需加载（跟 curator 一个套路）。
- 因为不新增可执行能力面、不动权限闸门，A2a **可以先做**，是路 B 里性价比最高、最安全的一半。

**A2b——可执行工具类（写代码变成新工具，排期靠后）**
- 产物是**真能跑的新工具**——写进工具注册表、未来会话直接调，等于给 agent **持久新增能力面**。
- 这一半**不能裸做**，须先铺底座：**PTC + CaMeL 受限解释器**（把自造工具的执行关进能力受限的解释环境）+ **沙箱能力分级**（见 §4）+ **一次性人审门**。底座没铺好之前，A2b 只能停在"临时脚本一次性跑"（下述弱版本），不做持久化。
- **已有（弱版本，今天就能干）**：小蛇有 `run_command`，能"写个脚本跑一下"当**一次性工具**（你批准即可）——这条不持久化、不改安全模型，是 A2b 的安全下限。
- **缺（强版本）**：把临时脚本**固化成正式、可复用的工具**——干净做法是 `user_tools/`（或"技能"）文件夹启动时**自动加载**（跟自动读 `mcp.json` 一个套路），但"自动加载 = 进下次会话声明"，不即时热插（见 §3 字节冻结）。

## 3. 核心风险：为什么这是全项目最大的安全升级 ⚠
现有**所有护栏**（三态权限闸门、污点追踪、`_is_sensitive` 硬拒、`_cmd_hits` 密钥扫描、`taint_gate`）都建立在一个前提上：
**工具是一套"已知的、我们策划过的"集合，闸门按工具名放行/拦截**。自装/自造工具**直接动摇这个前提**：
- **能力面失控 → 默认档必须反转**：一个能凭空造工具/装工具的 agent = 能**给自己开任意新能力**，绕开策划集。`SAFE_TOOLS`/`READONLY_TOOLS`/`_TAINT_HIGH_RISK` 这些**按工具名写死的白/黑名单，对"未知新工具"全部失效**（名字不在表里，现有逻辑等于默认放行、不加污点）。**定论：对未知新工具，权限默认从"黑名单已知高危"反转为"白名单已知安全、其余一律最保守档（`ask` + 打污点）"**——即"未登记 = 最不信任"，而非"未登记 = 放行"。
- **供应链风险**：装 GitHub 代码 = 在甲方机器上**跑第三方代码**（隐蔽后门、投毒依赖）。系统层面这类正是高危区。
- **自我改造**：造工具 = 自修改。一旦持久化，下次会话它已不是我们审过的那个它。
- **闸门盲区**：新 MCP 工具默认走 `ask`，但工具**描述本身**可能是 tool-poisoning 注入（已有 MCP 硬化经验可复用）；自造工具若不过沙箱，等于 `run_command` 的持久化超集。
- **会话内字节冻结（缓存约束）**：装的/造的工具**绝不能在当前会话即时生效**——一旦生效就改了工具声明的字节，打破 `prompt_cache_key` 依赖的稳定前缀缓存（前缀一变，整段 KV 缓存作废、每轮重算重计费）。**定论：新工具一律"下次会话"才进声明，当前会话工具声明字节保持不变**（装/造的动作本回合只落盘产 `pending`，不改运行时工具表）。

**结论：不是不能做，是必须"人始终在环"——每个新来源、每个新工具，甲方点一次头；纯计算类自造工具跑沙箱硬隔离，要碰 UI/文件的工具则走 `taint_gate` + 人审（沙箱选型见 §4）。**

## 4. 分阶段路线（先易后险，每阶段 TDD + 对抗审查 + 真机验收，符合项目纪律）

### 阶段 1（推荐先做）：路 A 安全版——"提议装，甲方拍板"
- 新工具 `propose_tool_install(需求/关键词)`：搜 MCP registry/GitHub → 返回**候选 + 来源 + 用途 + 一眼摘要**给甲方看。
- 甲方批准后才 `git clone`/装 + 写 `mcp.json` + 重连；**小蛇绝不自作主张跑陌生代码**。装好的工具遵守**字节冻结**：本会话不即时生效，下次会话才进声明（见 §3）。
- 复用现成 MCP 机制，风险可控，性价比最高。信任决策=人做。

### 阶段 2 = A2a（可与阶段 1 并行早做）：造"技能类"工具——纯 markdown，无沙箱
- 产物是 `SKILL.md` 技能卡，**不含可执行代码**、不新增能力面 → **不改安全模型、无需沙箱**。
- 落地：接**现有 `spawn_subagent` + Reflexion**，让子 agent 把成功经验固化成技能写进技能库。
- **background fork 自动学习写出的技能一律只产 `pending`，须人审后才激活**（呼应 curator 与人在环，绝不自动上线）；激活后同样走**字节冻结**、下次会话才进声明。
- 低风险、短路径，是路 B 里先能吃到的一半。

### 阶段 3 = A2b（深水，往后放）：造"可执行工具"——须先铺底座
铺底座之前，A2b 只允许**弱版本**：`run_command` 写脚本**一次性跑**（甲方批准即可），不持久化 → 不改安全模型，是 A2b 的安全下限；只需在文档/提示里把"用代码当一次性工具"这条路显性化 + 给个惯用法。
持久化的**强版本**须先具备三样底座，缺一不做：
- **受限解释器底座**：**PTC + CaMeL**——自造工具的代码关进能力受限的解释环境执行，而非裸跑。
- **沙箱能力分级（选型定案）**：
  - Windows 用 **AppContainer + Job Object**（Win11 Home 可用，**默认拒绝一切**）；Mac 用 **sandbox-exec**。
  - **但 AppContainer"默认拒绝一切" + UIPI 会挡死"要驱动 UI / 读写 ROOT 工作区"的工具**——所以**沙箱只关纯计算类自造工具**；**要碰 UI/文件的工具不塞进 AppContainer**，改走现有 `taint_gate` + 人在环审批。即按能力分两档：纯计算→沙箱硬隔离；触 UI/文件→闸门 + 人审。
- **一次性人审门**：小蛇写的新工具文件，须甲方**审一次**才激活（像 code review）；`user_tools/` 启动自动加载（镜像 `mcp.json` 加载路径），但加载 = 进"下次会话"声明、不即时热插（字节冻结见 §3）。
- 权限默认：未知新工具一律**最保守档**（`ask` + 打污点，见 §3 默认反转）；用咱们的**多 agent 对抗审查**给每个自造工具兜底（正好是它的用武之地）。

## 5. 动代码前要钉的决策（对抗审查已钉死的记 ✔，仍待甲方拍板的记 ？）
1. **走哪条**（？）：只装现成（A）/ 能自己造（B）/ 两个都要按阶段来？——方向仍待甲方定。
2. **A2a / A2b 边界**（✔ 已钉）：路 B 拆两条独立子线——**A2a=技能类（`SKILL.md`，无沙箱、接 `spawn_subagent`+Reflexion，可早做）**；**A2b=可执行工具类（须先有 PTC+CaMeL 受限解释器 + 沙箱能力分级 + 一次性人审门，排期靠后）**。两者不混做。
3. **自主度**（？+✔）：粒度仍待定，但**下限已钉**——**background fork 自动学到的技能/工具一律只产 `pending`，绝不自动激活**，人审是硬门。
4. **沙箱能力分级**（✔ 已钉）：Windows=**AppContainer + Job Object**（Win11 Home 可用、默认拒绝一切），Mac=**sandbox-exec**；**沙箱只关纯计算类自造工具**，**触 UI/文件的工具不进 AppContainer**（UIPI + 默认拒绝会挡死），改走 `taint_gate` + 人审。
5. **未知工具默认档**（✔ 已钉）：按名写死的白/黑名单对未知工具失效，故**默认反转为"白名单已知安全、其余一律最保守档（`ask` + 打污点）"**。
6. **字节冻结时机**（✔ 已钉）：装/造的工具**当前会话不即时生效、声明字节不变**，一律**下次会话**才进工具声明，护住 `prompt_cache_key` 稳定前缀缓存。
7. **审批 UX**（？）：新来源/新工具怎么呈现给甲方看、怎么一键批/拒？——待定。
8. **持久化与信任边界**（？）：装过的来源记在哪、怎么标"已信任"、能不能撤销？——待定。

## 6. 明确不做（边界，防跑偏）
- 不无人值守自动跑陌生 GitHub 代码；不自动装未经甲方点头的来源。
- 自造工具不绕过现有权限闸门/污点/敏感硬护栏；未知工具一律最保守档（默认反转为白名单已知安全）。
- 不把"能造工具"这件事本身做成默认开启——须显式开启 + 人在环。
- **background fork 学到的技能/工具不自动上线**：一律产 `pending`、人审后才激活；且工具不在当前会话热插，均下次会话生效（字节冻结）。

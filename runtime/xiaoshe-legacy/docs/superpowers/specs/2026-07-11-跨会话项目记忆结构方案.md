# 跨会话项目记忆结构方案 · 大项目跨多次对话如何保持连贯

> 状态：**规划中，先不做，待甲方拍板**（2026-07-11 记）。甲方提出：大项目正常要多次对话才能做完，
> 应该有个"共享的项目总记忆 + 每次对话各自的工作区"的结构，让每次对话都能读总记忆、了解全局。
> 本稿把现状、真正的短板、目标结构、设计问题钉清楚，供后续 brainstorming 起步。
>
> **2026-07-12 补：已跑一轮"实施前对抗审查"，把其技术定论织进本稿（短板 1/4/5、目标结构 A、§5 决策 1–4）。**
> 定论一句话：这不是"给记忆加个分区"，而是一次**协调的 v2 schema 迁移**——`memory.json` 从扁平 `list[str]` → `list[dict]`，
> 一次性定死字段全集、配迁移器与双读兼容、把 git 合并从"字符串并集"升级为 DELETE-aware、把 `source` 立为贯穿所有写入路径的硬不变式。
> **方案方向仍是"先不做待拍板"；织进来的是"一旦做，工程与安全上必须这么做"的边界，别让实施时踩坑或返工。**

## 0. 一句话
甲方直觉（"A 文件夹存项目总记忆，每次对话开新文件夹 B/C，但都能读 A"）= 教科书级正确的
**"共享项目大脑 + 每会话工作区"**模式。**小蛇其实已经有这套的一半骨架**，真正决定"跨对话推进得好不好"的
**不是文件夹怎么分，而是①总记忆里放什么 ②会话末怎么把学到的提炼回写 + 剪掉过时的**——这两点是当前短板。
而"①的落地"不是加个标签就完事，是一次**把 `memory.json` 从 `list[str]` 迁到结构化 `list[dict]` 的 v2 schema 升级**
（定字段全集 + 迁移器 + DELETE-aware 合并 + `source` 硬不变式）——这是本方案工程量最重、最该先钉死、也最容易返工的部分（详见短板 1/4/5、§5）。

## 1. 现状盘点（已有的一半 vs 缺的一半）
小蛇现在的落盘结构（`config.ROOT` + `.state/`）：
- **全局跨会话记忆** `memory.json`（`memory.py`：`system_message()` 每次开新会话把记忆事实注入置顶 system；`remember` 工具写入；上限 200 条防注入刷爆）——**这就是甲方说的"A 文件夹/项目大脑"，已存在、每次对话都读**。
- **每会话档案** `.state/sessions/<id>.json`（`session.py`：list/load/save/resume，现已 100+ 份）——**这就是"每次对话的 B/C"，已存在**（只是文件不是文件夹）。
- **情节记忆** `.state/episodic.jsonl`（`episodic.py` Reflexion：失败时自动写教训，下轮注入）——跨会话学习的**半个版本**。

→ 结论：**"共享总记忆 + 每会话记录 + 都读总记忆"小蛇已经是这个结构了**，甲方独立想到了已实现一半的正确架构。

## 2. 真正的短板（决定跨对话连贯性的，是这些，不是文件夹）
1. **总记忆是"平铺事实"，不是"结构化项目大脑"——补法是一次协调的 v2 schema 迁移，不是逐字段叠加**：
   `memory.json` 现为**扁平 `list[str]`**（见 `memory.py`）。大项目跨几十次对话时，扁平列表越堆越糊、检索不到重点。
   理想的项目大脑应分区：**目标 / 关键决策 / 当前进展 / 待解问题 / 已完成清单 / 约定**。
   **关键判断：这不是"给字符串挂个分区标签"能收场的，而是 `list[str]` → `list[dict]` 的一次性 schema 升级，且必须一口气把字段全集定死**——
   每条事实带 `id`（稳定标识，跨机合并/去重/被取代都靠它）、`source`（来源，见短板 5）、`created_at`、`invalid_at`（失效时间＝软删）、
   `superseded_by`（被哪条取代）、`strength`（强度/置信）、`helpful`·`harmful` 计数（被用到时有用/有害的反馈）。
   这些字段是后续一堆记忆增强（剪枝、失效、强化、被取代链、跨机确定性合并）**共用的地基**：一次到位，后面每个增强只写逻辑；
   若逐个字段慢慢加，等于对 `memory.json` 反复做迁移，每次都要动 `load`/去重(`_norm`)/`merge_facts`/`resolve_conflict_file` 四处，代价倍增且极易漏改。
   **所以升级的第一步是"定 v2 schema 全集 + 写迁移器 + load 双读兼容"，不是先做分区、日后再回头补字段。**
2. **缺"会话末提炼回写 + 剪枝"**：没有一个显式动作，在对话收尾时把这次会话（B/C）里**值得长期记的**升华进总记忆（A），
   同时**剪掉过时/已失效的**。`episodic` 只在失败时自动写教训——是半个版本。**总记忆只堆不炼 → 变噪音，agent 反而找不到重点。**
   （注：v2 的 `invalid_at` 软删 + `superseded_by` 取代链正是给"剪枝"备的机制底座，见短板 1。）
3. **不"提示"**：小蛇默默读总记忆、默默存会话档，不告诉用户"我正在读项目记忆 / 已归档本次会话"。甲方注意到的"没有类似提示"即此。
4. **git 自动合并是"字符串并集"，对"删除/被取代"的语义正好反了——这是一个真缺口**：
   多机现经 git 同步 `memory.json`，冲突走 `merge_facts` / `resolve_conflict_file`，做的是**字符串并集**（两边都留、去重保序）。
   平铺 `list[str]` 时这没错、也已过对抗审查加固。但 v2 一旦引入"软删（`invalid_at`）/ 被取代（`superseded_by`）"，
   **一台机器上删掉或取代一条事实，git 并集会在合并时把那条旧事实从另一侧原样捞回来复活——本意是"删"，结果却是"留"，语义完全反了。**
   必须把合并从"字符串并集"升级为**按稳定 `id` 的 DELETE-aware 确定性三路合并**：同 `id` 的多个版本按 `max(created_at)` / 尊重 `superseded_by`
   取胜者、识别并保留删除/失效标记，而不是无脑取并集。**这是 v2 迁移里一个不能漏的正确性缺口，不是可选优化。**
5. **记忆是"无闸写入 + 注入最高信任 system 段"，会话末自动提炼会把污点内容洗白成跨会话可信记忆（MINJA 面）**：
   `remember` 是 SAFE **无审批**写入，而 `system_message()` 把记忆**置顶注入 system**——最高信任层。
   短板 2 想要的"会话末提炼回写"一旦自动化，会把**本会话里 web_fetch / OCR 等抓来的外部数据（污点内容）**自动升华成跨会话"可信"记忆，
   下次开场就以最高信任身份注入——这是经典的**跨会话记忆投毒（MINJA）**：一次会话读到的恶意网页，能把指令写进"项目大脑"，污染后续所有会话。
   **缓解靠 v2 的 `source` 字段（见短板 1）：每条记忆标来源；`tool_output` / `web_untrusted` 来源的记忆注入时保留"外部数据"前缀、不进最高信任段，
   只有 `user_direct` / `agent_reflection` 之类可信来源才进置顶可信区。** `source` 必须作为**贯穿所有写入路径的硬不变式**存在，见 §5.3。

## 3. 参照：这正是 Claude Code 的 memory/ 目录做法
用户与 Claude Code 协作时用的 `.claude/projects/<proj>/memory/`：`MEMORY.md` 当索引/大脑 + 每条事实一个文件，
**每次会话末由 agent 提炼 + 剪枝**，外加每次对话的转录。**"结构化大脑 + 会话末提炼"这套用户已经跑通了**——
把它搬给小蛇，就是本方案的目标。

## 4. 目标结构（草案，待 brainstorm 细化）
- **项目大脑（A）**：从扁平 `list[str]` 升级为 **v2 结构化 schema（`list[dict]`）**——分区（目标/决策/现状/待解/已完成/约定）
  + 每条带 `id / source / created_at / invalid_at / superseded_by / strength / helpful·harmful`（**字段全集一次定死**，见短板 1）；带一个索引；小、高信噪、被策划。
  配套两件**必须与 schema 同批交付**的东西：①**迁移器**——把老 `list[str]` 条目转 v2：`source="legacy"`/`"unknown"`（**不是 `user_direct`**，别把来路不明的旧事实当用户亲授）、
  `created_at=memory.json 文件 mtime`、`invalid_at`/`superseded_by` 置空、默认落"约定/杂项"区；②`load()` **双读兼容**——能读老 `list[str]` 也能读新 `list[dict]`，
  滚动升级不炸旧档、旧机（同步的 git 里可能新旧并存）。
- **每会话工作区（B/C…）**：现有 `.state/sessions/<id>` 可升级为**目录**，装该会话的档案 + 产出 + 便签（比单 JSON 更能放富产物）。
- **提炼回路**：会话收尾（或 `:done`/退出时）触发"读本会话 → 抽出值得进大脑的 → 更新 A + 剪枝"，可半自动（agent 提议、用户点头）。
- **提示**：开场露一行"已载入项目大脑（N 条）+ 接续会话 X"，收尾露"已把 K 条学习并入大脑、剪 M 条过时"。

## 5. 动代码前要钉的决策
> 下面 **1–4 是实施前对抗审查已经定论的技术/安全不变式**——一旦动代码就照此落地，不是开放问题；**5–10 才是仍需 brainstorm / 甲方拍板的方向题**。

### 已定（对抗审查定论，动代码即照此实现）
1. **v2 字段全集与迁移默认值（一次到位，杜绝逐字段迁移）**：`memory.json` = `list[dict]`，每条至少含
   `{id, source, created_at, invalid_at, superseded_by, strength, helpful, harmful, zone, text}`（`zone` ∈ 目标/决策/现状/待解/已完成/约定）。
   迁移器把老 `list[str]` → v2：`source="legacy"`（或 `"unknown"`，**绝不是 `user_direct`**）、`created_at = memory.json 的文件 mtime`、
   `invalid_at = superseded_by = null`、`strength` 给默认值、默认落"约定/杂项"区。字段一口气定死，是因为它们被后续所有记忆增强共用（短板 1）。
2. **git 合并的 DELETE 语义（真缺口，必修）**：多机合并**不再用字符串并集**；改按稳定 `id` 做**确定性三路合并**——
   同 `id` 取 `max(created_at)` 的版本 / 尊重 `superseded_by` 取代链 / 识别软删（`invalid_at`），结果确定、幂等；
   **杜绝并集把已删或被取代的旧事实复活（否则删除语义正好被反转，见短板 4）。**
3. **`source` 硬不变式（贯穿所有写入路径，堵 MINJA）**：任何写记忆的路径——`remember`、会话末提炼回写、冲突合并/迁移——**都必须带 `source`**；
   注入时 `tool_output` / `web_untrusted` 来源**保留"外部数据"前缀、不进最高信任 system 段**，只有可信来源进置顶区（短板 5）。
   这是**安全不变式，不是可选项**：无闸写入 + 最高信任注入的组合，缺了 `source` 就是把 MINJA 面敞开。
4. **双读兼容 + 同步重写四处 + 保留上限**：`load()` 同时能读老 `list[str]` 与新 `list[dict]`（滚动升级、旧机/旧档不炸）；
   迁移**同批重写 `_norm`（去重改按 `id`/内容而非整串）、`merge_facts`、`resolve_conflict_file`**，
   让这些函数里**已过对抗审查的加固**（原子写 `atomic_write_json`、坏档隔离 `load_or_quarantine`、"两侧全对才写盘"、文件锁 `_LOCK_TIMEOUT`）**不被这次迁移打断或回退**；
   **`_MAX_FACTS`（200 条上限，防注入刷爆持久注入面 #38）继续保留**。

### 待拍板（brainstorm 起步）
5. **A 放什么 vs B/C 放什么**：项目大脑的分区（`zone` 全集已在 §5.1 定字段，但"什么算值得进大脑"仍需定标准）——决策/现状 yes，流水账 no，边界待议。
6. **提炼是自动还是半自动**：会话末自动提炼有注入/误提炼风险（大脑是持久注入面，已有 `_MAX_FACTS` / 中和经验，且 §5.3 的 `source` 不变式在自动路径下仍必须成立）；建议 agent 提议、用户拍板。
7. **剪枝的判定与触发**：过时/被推翻的**用什么机制识别**已定（v2 的 `invalid_at` 软删 + `superseded_by` 取代链 + `strength`/`harmful` 反馈，见 §5.1）；仍待定的是**由谁判定、何时触发**（会话末？定期？agent 提议＋用户点头？）。
8. **文件 vs 文件夹**：会话档升级成目录值不值得？大脑分区用单文件多段还是多文件+索引（对齐 Claude Code）。
9. **多对话并发**：多个对话同时开时（如并行会话），怎么避免同时写大脑打架（已有 `episodic.jsonl.lock` 经验可复用；§5.2 的确定性合并也让并发写更好收敛）。
10. **跨机**：大脑随 git / `.state` 备份怎么走——合并的 DELETE 语义已在 §5.2 定死，仍待定的是 `memory.json` 是否**重新纳入 git 跟踪**（现为本地 gitignore，见 DG-7）。

## 6. 明确不做（边界）
- 不让总记忆无限膨胀（保留 `_MAX_FACTS` 之类上限 + 剪枝）。
- 提炼回写默认**人在环**（agent 提议、用户点头），别让一次对话的噪音/注入自动污染项目大脑；**且无论自动半自动，回写都必须带 `source`（§5.3 硬不变式），污点来源不进最高信任段**。
- 不破坏现有 resume/压缩/缓存不变式（大脑注入进置顶 system，须与"base64 永不进 history"等不变式相容）。
- **v2 迁移不得回退 `memory.py` 里已过对抗审查的加固**（原子写、坏档隔离、"两侧全对才写"的冲突解析、文件锁）；也不得让新的 `list[dict]` 合并退化回"字符串并集"而复活已删/被取代的事实（§5.2/§5.4）。

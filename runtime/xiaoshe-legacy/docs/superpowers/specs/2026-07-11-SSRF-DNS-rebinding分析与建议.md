# SSRF · DNS-rebinding 残余风险：分析与建议（2026-07-11）

> 优先级 4 第二半"DNS-rebinding SSRF"的调研结论。**结论先行：这条的"正主"修法被本架构的强制代理堵死，
> 不是靠一次客户端代码改动能真正关掉的。本次不盲改，先把真相和选项摆清楚，等甲方拍板。**

## 现在已经有的 SSRF 护栏（`harness/web.py`，都真机/单测验过）
`is_safe_url` 只放行公网 http(s)，已覆盖：
- 拒非 http 协议、非法 host 字符（`{}[]` 等 glob/注入）、控制字符（`\r\n\t` 中段剥除分歧，#9）。
- 拒 localhost / `.local` / `.internal` / `.localhost`。
- 拒 IP 字面量里的环回/内网/链路本地/保留段，**含 curl 认的非常规数字编码**（十进制 `2130706433`、hex、0 前导八进制、短式）。
- 拒 `100.64.0.0/10`（CGNAT/阿里云元数据 100.100.100.200，走 `ip.is_global`，#4）。
- **重定向已逐跳复校验**：不使用 `curl -L`，改由 curl 输出 `%{redirect_url}`、Python 层对每一跳重过 `is_safe_url` 再手动跟（最多 4 跳）。→ 重定向型 SSRF 已堵。

## 残余缺口：DNS-rebinding / 域名解析到内网
`is_safe_url("http://attacker.com")` 遇到**真域名**（含字母）直接放行、**不做 DNS 解析**。之后真正取回时由
curl/代理再去解析这个域名 → 攻击者可让它解析到内网（`169.254.169.254`、`192.168.x.x`、`127.0.0.1`）。两种子情形：
1. **静态**：域名 A 记录常驻指向内网。
2. **rebinding**：校验时刻解析到公网（过 is_safe_url），取回时刻 DNS 翻转成内网（TOCTOU）。

## 为什么"标准修法"在本架构里无效 ⚠
教科书修法 = 在 Python 里解析一次域名 → 校验 IP 全公网 → 用 `curl --resolve host:port:IP` 把连接**钉**到这个已验证 IP。
**但本 harness 的 web_fetch 是强制走 HTTP 代理的**（`config.PROXY` = Clash `127.0.0.1:7897`，`curl -x $PROXY`）。走 HTTP 代理时：
- http:// → curl 把整条 URL 交给代理，**由代理解析域名并连接**；
- https:// → curl 发 `CONNECT host:443` 给代理，**仍由代理解析域名并连接**。

也就是说 **DNS 解析发生在代理侧，不在 curl 侧**。`--resolve` 只钉 curl 自己的解析缓存 → **走代理时被完全绕过**。
所以客户端的 IP 钉定对 rebinding **无效**：代理会独立再解析一次，攻击者的翻转照样生效。

## 唯一还能落地的部分（价值有限）
在 `fetch()` 里加一个**失败即放行（fail-open）的 Python 侧解析预检**：解析域名 → 若解析出的 IP 有任意一个非公网就拒。
- 能挡住 **① 静态**（域名常驻指向内网/LAN/路由器/localhost）——桌面部署下这是**真实**向量（域名指到 `192.168.1.1` 路由后台、`127.0.0.1` 本地服务）。
- **挡不住 ② rebinding**（代理会在取回时重解析、拿到翻转后的内网 IP）。
- 代价：给每次真实抓取加一次 DNS 往返（延迟/偶发抖动）；且要动到**安全关键路径**的现有 fetch 单测（注入 resolver 保水密）。
- 风险：fail-open 保证不误伤正常抓取，但毕竟是在安全关键码上改，无人值守夜里盲改不稳妥。

## 建议（给甲方三选一）
1. **在代理侧解决（最干净）**：Clash 配一条规则，把内网/环回/链路本地网段（`127.0.0.0/8`、`10/8`、`172.16/12`、`192.168/16`、`169.254/16`、`100.64/10`）一律 REJECT。代理才是真正解析+连接的一方，从这里堵才治本、对 rebinding 也有效。**推荐优先做这条。**
2. **加 Python 侧静态解析预检（fail-open）作纵深防御**：接受它只挡"静态指向内网"、挡不住 rebinding-through-proxy 的现实，作为②的补充。需 TDD + 注入 resolver 改造现有 fetch 测试。**想让我做就说一声，我按 TDD 稳着来。**
3. **接受残余、维持现状**：现有护栏已挡住 IP 字面量/数字编码/重定向/glob 全部向量；DNS-rebinding 需要攻击者控制一个域名的权威 DNS 且能翻转、且本机代理能路由到目标内网——在桌面单机 + Clash 出网代理下，实际可利用面窄。web_fetch 默认还需用户 ask 批准。

## 我的倾向
**选 1（代理侧 REJECT 内网）为主 + 可选 2 作纵深**。纯客户端代码改动无法真正关掉 rebinding（代理独立解析），
硬在客户端堆逻辑既不治本又给安全关键路径添风险。这条我判定为**架构层决策**，留给甲方拍板，没有夜里盲改。

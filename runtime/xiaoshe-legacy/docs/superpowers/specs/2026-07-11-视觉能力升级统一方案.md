## 第一层：外部 SOTA 研究（20 条经核实发现，按五主题）

### 一、感知 / 操作（grounding，核心命脉）

> **⚖️ 实施前对抗审查定论（A12 深挖后收口，落地时按此走）**：
> - **grounding 收口为一条轴、从 Set-of-Mark(SoM) 起步**：A12 后续深挖确定 **SoM**（在截图上用 UIA/OCR 的框画上编号、让 Kimi 回「点几号」而非报坐标）是「OCR 词框中心点击」的**上位版**。因此**不要先单独建「OCR 词框 grounder + bbox 中心点击」再返工**——把它并进 **SoM 一条轴**：SoM 起步，OCR 词框只是 SoM 的**框来源之一**（UIA 节点框、OCR 词框都往 SoM 喂）。下表 RegionFocus 与内部白捡的 OCR/bbox 零件都归到这条轴上。
> - **裁剪-重问统一成一个子系统**：**RegionFocus（本条）、zoom、Chain-of-Ground、FOVEA（A9）是同一「裁剪→放大→重问→迭代」机制的不同侧面**，落地时**做成一个统一子系统**、别各建各的。
> - **Mac 视觉覆盖近零、需独立排期**：本区的 grounding 手段（UIA 节点、OCR 词框、SoM 画框）在小蛇里全走 **Windows 路径**（UIA/System.Drawing/WinRT），**Mac 侧近零覆盖、要单独排期**——别默认跨平台白得。

| 发现 | 强在哪 | 怎么落 | 需要 | 性价比 |
|---|---|---|---|---|
| **RegionFocus 裁剪-重问**（arXiv 2505.00684） | 直击 Kimi「密集 UI ~40px 误差」：粗定位→按框裁剪放大→再问；开源模型上 ScreenSpot-Pro +28% | 现成区域截图加「裁剪→重问→聚合」循环，仅 a11y 打不到纯像素图标时触发；**落地并进统一「裁剪-重问」子系统**（与 zoom / Chain-of-Ground / FOVEA-A9 同一机制，别各建各的） | 零依赖，每次多 1–2 次 Kimi 请求 | **高** |
| **OmniParser V2**（microsoft/OmniParser） | 补 a11y 盲区（自绘/Canvas/游戏/图标无 UIA 节点），给 Kimi 编号元素清单按序号选 | 新 `parse_screen`，仅 observe 返空时升级调 Replicate | ⚠️Replicate API+计费+**截图发第三方=隐私**，须默认关+同意+污点 | 高（有依赖） |

### 三、创作产出（全新维度，此前只会"看"不会"做"）
**3a 图形生成**：**Diagram-as-code（Mermaid 默认）**——Kimi 出 Mermaid/SVG/HTML→render_check 渲染截图→自评→报错回喂修（Repair 2–3 轮）；流程图/架构图比位图模型准（文字一定对、可 diff）。**零依赖，高性价比**。（**审查定论：所有产图/渲染截图工具照抄现有 `vision.put_image/spill`**，守「base64 永不进 history」不变式；渲染/画框/diff 底层走跨平台 `imaging.py`，别绑 Win-only System.Drawing。）｜**Nano Banana Pro（Gemini 3 Pro Image）**——把结构化内容→带正确文字的信息图/海报（老文生图死穴），⚠️Google key+按图计费+SynthID 水印，中高。｜**Recraft V3/V4 SVG**——唯一直吐可编辑矢量 SVG，⚠️外部 API，低（外围）。

**3b 设计到代码**：**ScreenCoder 三段式**（2507.22827）——补缺的「前端先验 Planning 层」(Grounding→Planning 布局 JSON→Generation)，接 render_check，零依赖，中。｜**UI2Code^N**（2511.08195）——UI→代码三态闭环(生成/编辑/打磨)+相对择优，Kimi 复刻零依赖(9B 模型需 GPU 不采纳)，中。

**3c 幻灯片**：**reveal.js/Marp 幻灯片即代码**——Kimi 直吐自包含 HTML deck，复用 render_check 闭环，免 python-pptx 坐标/EMU 易错点；reveal.js 路线零依赖，导出 .pptx 才需 Marp CLI(1 Node 依赖)。**高性价比**。｜**AutoPresent/SlidesLib**（2501.00912）——可编辑 .pptx 路(HTML 给不了)，抄其 10 个高层函数(MIT)让 Kimi 写十几行短代码走沙箱，⚠️需 python-pptx(1 轻 pip 依赖)，若真要 .pptx 交付则高。

## 第二层：向内源码审计（家里的半成品/白捡）
- **🔴 PDF 路在现代系统上是坏的**：`vision.pdf_to_png` 硬调 `sips`——Windows 没有、macOS 从 Ventura 起对 PDF 也损坏 → **read_image 读 PDF 两台机大概率都失败**。修法全研究透且**他机在本机 Windows 已真机跑通**（WinRT `Windows.Data.Pdf`，脚本在 scratchpad；Mac 用 osascript JXA+PDFKit），**顺带解锁多页**(page_range)。→「已知坏、修法在手、只差接线」，**该优先补**。
- **⭐ OCR 词级坐标 = 免费文字 grounder（→ 并入 SoM 轴）**：`Windows.Media.Ocr` 结果自带逐词 bbox(OcrLine/OcrWord)。配合 observe 已有的元素坐标 → 给"画在图上、a11y 看不到的文字"也算出可点坐标，**零新模型**补"看得见点不了"。**审查定论：不单独成器**——OCR 词框作为 **SoM 的框来源之一**并进 grounding 主轴（见 §一 定论），别先建独立 grounder 再返工。
- **⭐ bbox 中心点击兜底（→ 并入 SoM 轴）**：observe 已拿到每个 a11y 元素坐标(pos+size)，"有坐标但没 InvokePattern 的控件"可直接点 bbox 中心——**零新模型的半个 grounder**。同样并进 SoM 轴：SoM 编号背后的可点坐标即取自这些 UIA/OCR 框中心。
- **图片压缩也 Mac-only**：`downscale_to_max` 也硬调 sips → Windows 不压图、费 token。**审查定论：走跨平台 `imaging.py`**——把缩放/画框/diff 图这类产图能力收进一个纯标准库的跨平台 `imaging.py`，**别把 Win-only System.Drawing 当唯一路径**（System.Drawing 只作 Windows 后端之一）；这样 SoM 画框、diff 图、压缩共用一套、Mac 也有着落。**且所有产图工具照抄现有 `vision.put_image/spill`**，满足「base64 永不进 history」不变式。
- **recall 的 ocr_digest 字段闲置**：`put_image` 留了位没人填。现在有 ocr 了 → 自动给截图打文字指纹 → **按可见文字回捞截图**（"找那张显示了'登录失败'的截图"）。零依赖连招。
- **observe 抄几招零依赖**：新元素打 `*` 标记(browser-use，秒发现弹窗/动态变化)、类型化动作 ID 表(Notte I1/B3/L)、一句话验收 validate(Skyvern)、cap 60/1600 上限可调。
- 一些"未真机验证"注释已过时（Windows 截图本周验过）。

## 统一推进排序（拍板建议）

### 🟢 先做（零依赖 / 无需自训 / 直击核心，一批捆一起，都挂在渲染截图/observe 基建上互相加强）
1. **TVAE 动作核验**（自纠环）——升级小蛇**最核心**的原生 UI 操作回路，把「只汇报」变「先声明期望→后核验」，主动逮静默失败。低工零依赖高价值。
2. **🔴 PDF 修（WinRT/JXA）**——**这是修 bug**：现在两台机读 PDF 都可能失败，修法已真机验证，只差接线。顺带多页 + 图片压缩 Windows 化。
3. **UI-Bench 交付级 pairwise + AI 默认审美失败清单**（审美）——一句锚定 prompt + 自检清单把 render_check 审美拉到交付级。低工零依赖高价值。
4. **RegionFocus 裁剪-重问**（感知）——**唯一直击 Kimi「密集 UI ~40px」根本软肋**，纯用现成截图裁剪。中工零依赖高价值。**落地并进统一「裁剪-重问」子系统**（zoom / Chain-of-Ground / FOVEA-A9 同机制，一次做成一个子系统，别各建各的）。
5. **SoM grounding 轴（起步）**（感知，内部白捡）——零新模型补「看得见点不了」的一大子集。**审查定论：grounding 收口为一条轴、从 Set-of-Mark 起步**（截图上画编号框、Kimi 回「点几号」），**「OCR 词框 grounder + bbox 中心点击」并入本轴**当框来源，**别先单独建 grounder 再返工**（SoM 是其上位版）。
6. **一批零依赖 render_check/observe 升级捆一起**：Vision-Guided 视觉评审环 + ReLook 两护栏 + MLLM UI Judge 9 因子 + PPTEval + Chart-to-Table 提示 + Mermaid 图表即代码 + reveal.js 幻灯片 + observe 的 `*` 新元素标记/validate。全零 API 零算力、低-中工，**性价比最高的一片**。

### 🟡 中大型工程 / 排期
- **Chrome DevTools MCP**——接一个 MCP 白得「网页操作+前端调试」一条轴（只需 Node.js），性价比其实很高，单列排期。
- 文档粗到细两段式、ScreenCoder Planning 层、UI2Code^N 三态——零依赖但要设计多步编排。
- **AutoPresent/.pptx**——加一个轻 python-pptx 依赖，取决于是否真要可编辑 .pptx。
- **OmniParser V2**——潜在高价值补 a11y 盲区，但要 Replicate API+桌面截图发第三方(隐私)，须先设计门控/污点/默认关，谨慎。
- **Nano Banana Pro 图像生成、Gemini 3.5 Flash CU 兜底定位**——外接 API+计费，可选后端按需接。
- **🍎 Mac 视觉路径独立排期**——**审查定论：Mac 侧视觉覆盖近零**。上面 grounding（UIA 节点/OCR 词框/SoM 画框）、产图/压缩（System.Drawing）、PDF/OCR（WinRT）在小蛇里**全是 Windows 路径**，Mac 对应件（JXA/PDFKit、Vision.framework OCR、Quartz 截图、CoreGraphics 画框、AX API grounding）**要单独排期真机验**，别默认跨平台白得。`imaging.py` 收口能省一部分，但 AX/OCR/PDF 的 Mac 后端仍需各自补齐。

### 🔴 暂缓 / 不做
- **一切要本地跑模型权重/训练的**：DeepSeek-OCR 本地模型、OmniParser 本地权重、UI2Code^N 9B、所有 LoRA/RVPO/SFT+GRPO——**需 GPU/训练管线，小蛇做不了**（好在其"思路/rubric/提示词结构"都能零依赖借用，模型丢掉即可）。
- **Recraft SVG**——外围低价值，确要矢量图标资产再说。

## 诚实标注（甲方最该看的三行）
- **破坏「近零依赖」的（需外接第三方 API + 计费 + 新信任面）**：OmniParser V2(Replicate+隐私)、Gemini CU(Google)、Nano Banana Pro(Google)、Recraft SVG。另 Chrome DevTools MCP 需 Node.js、AutoPresent 需轻量 python-pptx、Marp 导出需 Node。**其余全部零新增依赖。**
- **需算力/训练、小蛇根本做不了的**：所有本地模型权重与微调——可落地部分**只有其"思路/评分表/提示词结构"**，模型和训练一律排除。
- **🍎 平台覆盖：本方案的视觉能力当前近乎全是 Windows 路径**（grounding 的 UIA/OCR/SoM、产图的 System.Drawing、PDF/OCR 的 WinRT）——**Mac 侧覆盖近零、需独立排期真机验**，别默认「跨平台白得」；`imaging.py` 收口能省一部分产图代码，AX/OCR/PDF 的 Mac 后端仍要各自补。

**一句话给甲方**：先花小钱办大事——**TVAE + PDF 修 + UI-Bench + RegionFocus（并进统一裁剪-重问子系统）+ SoM grounding 轴（起步，OCR 词框并入）** 加上那批零依赖 render_check/observe 升级，不掏一分外部 API 费、不碰 GPU，就能把小蛇的「操作可靠性 / 文档阅读 / 审美判断 / 密集界面定位 / 看得见点不了」五块短板同时抬一档；接外部 API 的（Chrome DevTools MCP、OmniParser、图像生成）留到确有需求逐个拍板。

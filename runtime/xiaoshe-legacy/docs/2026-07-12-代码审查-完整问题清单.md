## 三、性能 / 成本 / 可维护性优化

### 性能与成本（按性价比排序）
- ⭐⭐⭐ **压缩预算 24000→512000（M1）**：长会话最大 token 省点，压缩次数从 5~15 次/会话降到 1~2 次。一行级改动。`compaction.py:19`。工作量小。
- ⭐⭐⭐ **非流式 curl retry 重复计费**：`--retry=5` 对 5xx-after-generation 重发非幂等 completion，最坏 6× 计费（压缩摘要/子 agent 走此路）。镜像 `_post_stream`：curl retry=0 + Python 层仅空 stdout+连接类退出码才重试。真机造 502 复验。`kimi_client.py:96-140`。中。
- ⭐⭐⭐ **PDF 转图 Windows 分支缺失**：`vision.py:116,78` 只依赖 macOS sips，主力 Win11 读 PDF 恒失败 + 大图未压缩多耗 35~46% token/张。加 WinRT `Windows.Data.Pdf` + `System.Drawing` 分支（零新依赖，须真机验证）。大。
- ⭐⭐ **render 两次浏览器冷启**：`render.py:158` DOM 无条件抓。加 `need_dom=bool(keywords)` 门控。别采"单条 chrome 合并"（未获保证）。小～中。
- ⭐⭐ **read_file 无大小上限**：`tools.py:33` 全量读内存+落 blob。加 `st_size` 闸门（8MB）超阈读头部。小。
- ⭐ report() 最近日志解析两遍：`usage_report.py:96`。单遍+缓存（保留 `totals()` 公开 API）。小。
- ⭐ fetch 无 Content-Length 整页读内存：`web.py:184`。Popen 增量读到 max_bytes+headroom 即 kill。小～中。
- **建议记录不修**（经核实收益极小或改法不安全）：`_tainted` 无上限增长（LRU 会破坏"污点不洗白"，唯一安全优化是按长度剪枝 span）、total_chars 每轮 json.dumps（被网络往返淹没）、一轮多 tool_call 串行（可并发的重 IO 工具恰好都是 ask 非 allow）、UIA 每操作冷启 powershell（常驻宿主有 DPI/WinRT 状态风险）、每轮 history 全量 fsync（被网络淹没）。

### F01｜[correctness] 非流式 _post 用 curl --retry 会对 HTTP 5xx/超时重发，非幂等生成被重复计费

- **问题**：注释断言「只留 retry（curl 仅对连接建立阶段的瞬时失败重试，响应已开始则不重发）」——这与 curl 实际行为不符。curl 的 --retry（即使不加 --retry-all-errors）把 HTTP 408/429/500/502/503/504 和超时都视作 transient error 并整请求重发。非流式路径 `retry=retry`（chat 默认 5）+ `max-time`/`retry-max-time=timeout`。当上游（或本项目强制经过的本地代理 Clash）在模型已开始/已完成生成后返回 502/504（网关类错误极常见于代理链路），curl 会在 retry-max-time 窗口内最多重发 5 次，每次都触发一次全新的非幂等 completion 生成。Kimi coding 按请求次数计费（见 usage_report.py:4 真机探针结论），故一次 5xx-after-generation 可放大到最多 6 倍计费。流式路径 _post_stream 已用 has_output 精心防住了这一点，但非流式路径的同一防护缺失、且注释给出了错误的安全承诺。（超时 exit 28 这条因 retry-max-time==max-time 恰好被边界卡住基本不会重试，故主风险是 5xx-after-generation，非超时。）
- **影响**：非流式调用（compaction 摘要、无 on_delta 的内部调用）在代理返回 5xx 时重复生成、重复计费，最坏 6×，且用户无感知；同时代码注释误导后续维护者以为该路径已安全。
- **修法/优化方案**：对齐流式路径的设计：非流式 curl 配置改 `retry = 0`（去掉 curl 层重试），把重试上移到 Python 层，仅当 stdout 为空且 curl 退出码属连接类 (7/35/56) 时才重试（此时绝无生成、重发幂等），对 exit 28 与任何已拿到 HTTP 响应体的情况一律不重试。即在 _post 里包一层与 _post_stream 同构的 while 循环，用 `_RETRYABLE_EXIT` 判定。同时改掉 line 96-98 的错误注释。属计费关键路径，改后须真机复验（构造代理 502 场景确认不再重发）。

### F02｜[correctness] stop_task 按裸 child_pid 强杀，PID 复用会误杀无辜进程（POSIX 上还会连累整个进程组）
- **位置**：`harness/schedule.py:369-382`
- **问题**：stop_task 从 pidfile 读出 child_pid（:369），仅用 _pid_alive(pid)（:370）判断是否在跑，然后 taskkill /T /F /PID（:376）或 os.killpg(int(pid), SIGTERM)（:380）。pidfile 只在 run_task 的 finally 里清（:336），若监工被 SIGKILL/断电等非正常终止，pidfile 会残留一个陈旧 child_pid。等 OS 把这个 PID 复用给某个无关进程后，_pid_alive 返回 True，stop_task 就会对这个无辜 PID 执行强杀——Windows taskkill /T 连它的整棵子树，POSIX killpg 连它所在的整个进程组一起杀。这是把'停我自己的任务'变成'杀别人的进程'。_pid_alive 的 PermissionError→True（:355-356）还会把属于别的用户/进程的复用 PID 也判成'活着'，进一步扩大误杀面。
- **影响**：用户级任意进程（乃至进程组）被误杀，且是静默的——只会打印一句'已发停止指令'。
- **修法/优化方案**：用已有的 per-task 文件锁作为'是否真有监工在跑'的唯一真相源，而不是裸探 PID。run_task 期间监工持有 _io.file_lock(RUNNING_DIR / name)。stop_task 里先尝试 timeout=0 非阻塞获取同一把锁：能拿到 → 没有监工在跑 → pidfile 是陈旧的 → 立刻释放并 unlink pidfile、返回 False（'没在跑，已清陈旧记录'），绝不 kill；拿不到（TimeoutError）→ 确有监工持锁运行中 → 此时 pidfile 里的 child_pid 一定是本次运行的真子进程、不存在复用 → 再走 taskkill/killpg。这样把'PID 存活'替换成'本会话的锁被占用'，从根上消除复用误杀。

### F03｜[performance] 压缩字符安全网(24000)远低于 token 预算(128000)，成为实际触发器→提前 5~20× 压缩，白烧摘要调用并击穿 prompt 缓存
- **位置**：`harness/compaction.py:19 (DEFAULT_BUDGET_CHARS=24000)，判定在 :117；预算 token 在 config.py:68=128000`
- **问题**：maybe_compact 的触发是 OR：`tok > 128000 or total_chars > 24000`。tok 通常远低于 128000，于是 total_chars>24000 这条几乎总是先命中，成为真正的压缩触发器。而字符网的立意（注释：防大 base64/长串骗过 token 估算）在本仓已基本失效——已核实 base64 从不进 history（vision.wire 只把图拼到临时副本尾部、history 只留 ~40 字指针），tokens.estimate_text 对普通 ASCII 也按 rest/4 计（与真 token 量级相当）。结果：中文会话 24000 字≈24000 token，英文/代码 24000 字≈6000 token，都在 128000 预算的 1/5~1/20 就触发压缩。每次触发=①一次完整的 _summarize Kimi 往返（额外计费+损失细节）②history[:]=pinned+[summary]+recent 改写了置顶 system 之后的全部消息，prompt_cache_key 按最长公共前缀命中，摘要点之后整段缓存全部失效、下一轮按全价重算。反而比让带缓存的 history 自然增长更贵（增长部分大多命中缓存只收折扣价，压缩却把后半段打回全价+多一次摘要调用）。
- **影响**：长会话最直接的 token 浪费点：每次多余压缩 = 一次摘要 Kimi 调用 + 摘要点之后全部上下文的一次缓存未命中全价重算。用户按 token 池计费，长任务里这是数千~上万 token/次的重复计费叠加。
- **修法/优化方案**：把字符网从『主触发器』还原为『病理兜底』，让 token 预算做真正的闸门：将 DEFAULT_BUDGET_CHARS 提高并做成可配置，例如 `DEFAULT_BUDGET_CHARS = config.get_int("KIMI_CONTEXT_BUDGET_CHARS", 4 * DEFAULT_BUDGET_TOKENS)`（≈512000，取 4 字符/token 最坏情形上界；中文场景 chars≈tokens 时 token 预算自然先命中）。这样正常长会话由 128000 token 预算触发、压缩次数从每长会话 5~15 次降到 1~2 次，既省摘要往返又保住缓存前缀。字符网仍在（挡真正异常膨胀的内容），只是抬到正常文本之上。

### F04｜[robustness] _cmd_hits 通配符前缀扫描过宽：valid*/grid*/android*/readme.e* 等常见命令被硬拒(deny)
- **位置**：`D:/ke/harness/permission.py:106-109`

### F05｜[robustness] 流式读循环无 connect/整体超时，Python 硬兜底 hard_timeout 实际不生效，curl 卡在 TLS 握手会永久阻塞
- **位置**：`harness/kimi_client.py:90-94 (流式配置) 与 171,175 (读循环与 wait)`
- **问题**：line 151 的 `hard_timeout = 2*timeout+30`「Python 侧硬兜底，防 curl 卡死永久阻塞」只作用在 line 175 的 `proc.wait(timeout=hard_timeout)`。但 line 171 的 `reassemble_stream(proc.stdout, ...)` 是一个 `for line in proc.stdout` 的同步阻塞读循环，它先执行、返回后才轮到 proc.wait。流式配置（line 90-94）刻意不设 `max-time`，也没有设 `connect-timeout`，只有 `speed-limit=1 / speed-time=timeout`——而 speed 检测只在传输已开始（已建连、已有字节流动）时才计。若 curl 卡在建连或 TLS 握手阶段（正是本项目已知的失败模式：注释 line 5 承认该站 TLS 重协商、Python OpenSSL 会握手失败），一个字节都没吐，speed-time 不触发、又无 connect-timeout，则 `for line in proc.stdout` 永久阻塞在 line 171，永远走不到 line 175 的 proc.wait，hard_timeout 形同虚设。唯一逃生口是用户手动 Ctrl+C。
- **影响**：弱网/代理黑洞/TLS 握手挂死时，交互式（流式）调用整体永久卡死，宣称的硬超时兜底不起作用，用户体验为「回车后无限转圈、无报错」。
- **修法/优化方案**：给流式 curl 配置补上 `connect-timeout = {timeout}`（或更短，如 min(timeout,30)），把建连+TLS 握手阶段封顶——speed-time 负责已建连后的空闲失速，connect-timeout 负责建连前的挂死，两者合起来才覆盖全程。若要更稳，另可把 stdout 读循环放到子线程并对主线程 join(hard_timeout)，超时则 kill curl。首选加 connect-timeout（零副作用、最小改动）。改后真机验证：对不可达代理端点发起流式请求，确认在 connect-timeout 秒内报错而非挂死。

### F06｜[robustness] MCP 非规整输出未做防御性解析，畸形 server 直接抛 AttributeError 逃逸软屏蔽
- **位置**：`harness/mcp_client.py:166-169 (call_tool) / :161-162 (list_tools) / :231-232 (connect)`
- **问题**：整个模块 docstring 立的威胁模型是"真实世界不守规矩的第三方 server"，但结果解析全部假设 JSON-RPC result 是规范形状：
(1) call_tool 第166行 `res = self._rpc(...) or {}`，若 server 回 `"result": "ok"`（字符串）或列表，`or {}` 不生效，res 仍是字符串，第167行 `res.get("isError")` → AttributeError。
(2) 第169行 `for c in res.get("content", [])`：若 server 回 `"content": "hello"`，迭代出字符 `c="h"`，第170行 `c.get("type")` → AttributeError；若 content 列表里混入非 dict 元素同样炸。
(3) list_tools 第162行 `(res or {}).get("tools", [])` 对非 dict truthy result 同样 AttributeError；tools 非列表 / 元素非 dict 时 connect 第232行 `t.get("name")` 炸。
关键危害：这些 AttributeError 不是 MCPError，call() 第278行 `except MCPError` 抓不到，于是 (a) 异常裸奔到 tools.execute，(b) _mark_down 不被调用——畸形 server 永远不被软屏蔽，每次调用都重复崩，彻底绕过了 2b 设计的失效保序机制。
- **影响**：单个不守规矩/恶意第三方 server 就能让工具调用路径非受控崩溃，且无法被软屏蔽，反复毒化后续调用。正是本模块声称要硬化的场景。
- **修法/优化方案**：在所有消费 _rpc 返回值处强制形状归一：
1) call_tool 开头 `res = self._rpc(...); res = res if isinstance(res, dict) else {}`。
2) `content = res.get("content"); content = content if isinstance(content, list) else []`；循环内 `if not isinstance(c, dict): parts.append("[非常规内容块]"); continue`。
3) list_tools：`res = self._rpc("tools/list"); tools = res.get("tools") if isinstance(res, dict) else None; tools = tools if isinstance(tools, list) else []; return [t for t in tools if isinstance(t, dict)]`。
4) connect 循环内对 `raw = t.get("name")` 前已能保证 t 是 dict（经上一步过滤）。
可选兜底：call() 把 `except MCPError` 放宽为 `except Exception`（非 MCPError 也 _mark_down 再重抛为 MCPError），确保任何解析异常都触发软屏蔽而非裸奔。

```
if isinstance(ip, ipaddress.IPv6Address):
    v = int(ip)
    embedded = ip.ipv4_mapped or ip.sixtofour
    if embedded is None and (v >> 32) == 0 and (v & 0xffffffff):  # ::a.b.c.d
        embedded = ipaddress.ip_address(v & 0xffffffff)
    if embedded is None and (v >> 32) == 0x0064ff9b:            # 64:ff9b::/96 NAT64
        embedded = ipaddress.ip_address(v & 0xffffffff)
    if embedded is not None and not embedded.is_global:
        return False
return ip.is_global
```

### F68｜[security] render 期间把整个 ROOT 目录树挂到 127.0.0.1 http 服务，渲染窗口内本机任意进程可拉取 ROOT 文件

### F69｜[security] 脱敏只匹配 Bearer 前缀且流式 stderr 完全未捕获，key 裸值或 curl 流式错误行不经脱敏

### F70｜[security] SSRF is_safe_url 对 NAT64 前缀 64:ff9b::/96 内嵌内网/元数据 IPv4 判为安全
